| 1 | Remediation recommended | The budget grace period can start late | 🐞 Bug, ≡ Correctness | hb/gateway.py | dismissed: the stored time is never later than any budget refusal the harness receives, and the grace period runs from the gateway's first refusal, as the file records it (spec §5.1 and §6.1 step 2, "the grace period runs from the time in the file"; hb/orchestrator.py:281-284). The mechanism is real: `admit()` decides under the ledger's lock (hb/gateway.py:218), `note_refusal()` takes the time outside any lock (:556), and `_change()` keeps the value of the first thread to take its lock (:277-280), so a first refusal paused before that point can lose to a later one. But each refused request sends its 429 only after its own `note_refusal()` returns (:713, then `_local`, `_answer` and `_send`, :1027-1052), and `_change()` returns only once the first value is saved (or its save failed, which stops the gateway with exit 1 and fails the job, :281-286), so every 429 goes out after the stored time. Measured locally with an instrumented copy of `note_refusal()` (not in the repository): request A paused 300 ms after its decision and request B refused 200 ms later stored B's time, 1 ms before the first 429 the client received. Taking the time under the admission lock, as suggested, would have started that grace about 200 ms before any refusal reached the harness, which is finding 2 made worse. | open |
| 2 | Remediation recommended | The budget grace period can start early | 🐞 Bug, ≡ Correctness | hb/gateway.py | dismissed: the grace period starts early by the time between taking the time and sending the 429: waiting for the state file's lock, writing that small file (a temporary file, then a rename, no fsync; hb/gateway.py:269-273), deciding the record and sending. Measured locally with an instrumented copy of `note_refusal()` and an unrounded clock (not in the repository), from the stored time to the client having the 429: 0.42 ms median and 8.7 ms at most over 150 refusals in a row, 5.6 ms at most over 50 concurrent ones. The grace period is 30 s, and the kill itself waits for a `docker container inspect` past the deadline and then a `docker kill` (hb/orchestrator.py:263-270). Killing the harness before it receives the refusal would need about a 30-second stall between taking the time and sending the 429. The suggested fix, taking the time where the refusal's record is decided with no state write between that and the send, moves the write after the 429: a refusal answered earlier but written later then loses the first-value race in `_change()` (:277-280), which makes finding 1 real, in the harness's favour, unless the earliest value is kept, and then the toolkit would have to move a deadline it sets only once (hb/orchestrator.py:281-284). The order is kept on purpose: the stored time comes after the decision to refuse and before every 429 the harness can receive. tests/test_gateway.py:1144-1157 checks that the stored time falls between sending the refused request and receiving its 429, and that a later refusal does not replace it; the order across concurrent refusals follows from the code above and is not tested. | open |
